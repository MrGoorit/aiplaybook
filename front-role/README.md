# AI Agent 工作区（项目级）

本目录用于沉淀“长期规则 + 任务模板 + 执行记录”，帮助小助手在每次任务中稳定输出，并避免上下文过载。

**和代码的关系**：`ai-agent/` 只放协作协议与文档，不写业务代码；本仓库前端业务实现在 `web/yes-one-api/src/` 等目录。任何人（产品、开发、使用 AI 的同事）都可以只读本目录，了解「怎么提需求、AI 会遵守什么」。

**产品经理专用**：若单独维护 `ai-agent-pm/` 等产品文档目录，可与本目录互补；本仓库以 `ai-agent/` 为开发与协作规则的真相来源。

## 目录与文件说明

下面按「文件夹 → 根目录文件」说明各自**含义、作用、谁该看、何时更新**。

### `rules/`（规则：必须遵守的边界）

| 含义 | 规定 AI 与开发「能做什么、不能做什么」，减少误改接口、大范围重构等问题。 |
| 作用 | 相当于本项目的「短总则 + 专题补充」：先保证不做错，再谈做得好。 |
| 典型内容 | `must-follow.md`：全任务通用（最小改动、不猜接口、输出结构等）。`frontend-rules.md`：前端专项（组件、表单、样式、并发等）。以后可按主题增加 `xxx-rules.md`。 |
| 谁该看 | 每次让 AI 写代码或改规则前，执行者应至少读过 `must-follow.md`；前端任务再读 `frontend-rules.md`。 |
| 何时更新 | 团队约定变化时（例如新增必须跑的检查、禁止动接口的路径）；发现 AI 屡次踩坑时，把教训沉淀成一条规则。 |

### `goals/`（目标：当前阶段要达成什么）

| 含义 | 描述「产品/协作上现阶段最关心什么」，不是具体任务清单。 |
| 作用 | 让 AI 的输出与团队优先级对齐，避免在次要方向上花大量 token。 |
| 典型内容 | `now.md`：长期方向 + 近期重点 + 可量化的「成功标准」示意。可按季度增加 `2026-q2-goals.md` 等。 |
| 谁该看 | 发起较大需求前扫一眼；迭代规划变更时由负责人更新。 |
| 何时更新 | 每季度或重大里程碑调整时；重大目标切换时务必改一版，避免文档与事实脱节。 |

### `templates/`（模板：任务怎么写、结果怎么报）

| 含义 | 可复制粘贴的空白结构，统一「开工前」和「收工后」的信息格式。 |
| 作用 | 减少口头需求、减少 AI 自由发挥导致的风格不一致。 |
| 典型内容 | `new-task.md`：任务开始前填写（背景、范围、验收、风险）。`task-log.md`：任务结束后对照填写或仅在对话中按此结构回复（已完成 / 未完成 / 风险 / 验证建议；有待办时含「接下来要做的事」，无则写「无」或省略）。 |
| 谁该看 | 产品写需求、开发拆任务时都可套用；不要求每次都保存成文件，但**结构建议一致**。 |
| 何时更新 | 团队协作方式变了（例如必须多填「回滚策略」）时，改模板即可全员对齐。 |

### `logs/`（日志：有价值任务的留痕）

| 含义 | **可选**落地的 Markdown 文件，记录某次重要任务的决策与结果。 |
| 作用 | 复盘、扯皮、 onboarding、向领导汇报时，有据可查；不是每次小改都要新建文件。 |
| 典型内容 | 按 `YYYY-MM-DD-<topic>.md` 命名；正文建议沿用 `task-log` 结构并补充背景链接。 |
| 谁该看 | 接手同模块的人、事后排查「当时为什么这样改」的人。 |
| 何时写入 | 涉及核心流程、重要交互、规则变更、或你判断「以后一定会有人问」时再写；日常一行改动可只写在对话里。 |

### 根目录 `README.md`（本文件）

| 含义 | `ai-agent` 的**总说明**：目录含义、使用顺序、命名规范、维护习惯。 |
| 作用 | 新人第一次打开仓库时的入口；命名习惯见下文「命名规范」一节（一句话版）。 |

### 根目录 `INDEX.md`（阅读入口 / 路由表）

| 含义 | 告诉执行者：**本次任务必读哪几份、按需读哪几份**，避免每次通读整个 `ai-agent/`。 |
| 作用 | 控制上下文体量：先读 INDEX，再按链接点开，和「翻书先看目录」一样。 |
| 谁该看 | 每次让 AI 执行任务前，人类或 AI 都应先扫一眼 INDEX。 |

### 根目录 `SKILL.md`（Cursor Skill 使用说明）

| 含义 | 说明 `.cursor/skills/` 里两个 Skill 叫什么、在什么对话里怎么用、会自动读哪些 `ai-agent` 文件。 |
| 作用 | 把「如何在 Cursor 里触发规范化协作」从 README 里拆出来，README 保持偏「结构与规范」，SKILL 偏「操作手册」。 |
| 详见 | [SKILL.md](./SKILL.md) |

### 根目录 `queued-tasks.md`（对话任务清单）

| 含义 | 把要在对话里交给 AI 的指令按「任务一、任务二…」写好，需要时 **@ 本文件** 并说明执行第几条，减少每次手打长指令。 |
| 作用 | 个人或小组的轻量 backlog；与 `templates/new-task.md`（单次任务开工模板）互补，本文件偏**可复用的多条指令库**。 |
| 谁该看 | 经常重复同类需求、希望固定「Skill + 路径 + 描述」写法的人。 |
| 何时更新 | 新增待办、完成一条后勾选/删除、或调整某条措辞时。 |

### 与 `.cursor/skills/` 的关系（简要）

- **`.cursor/skills/*/SKILL.md`**：Cursor 识别的**入口**，内容通常很薄，指向要先读 `INDEX.md`、`rules/` 等。
- **`ai-agent/SKILL.md`**：给人看的**说明副本**，与入口职责相同，便于在仓库里搜索与 Code Review；以 `.cursor/skills/` 中实际 `SKILL.md` 为准做触发。
- **`ai-agent/`**：**规则与模板的真相来源**；改协作方式时优先改这里，再视需要改 `.cursor/skills/` 入口里的措辞。

## 使用顺序（推荐）

1. 先读 `INDEX.md`（1 分钟内了解本次应读哪些文件）。
2. 必读 `rules/must-follow.md`（短总则，不超过一页）。
3. 按任务类型读取对应模板（只读相关文件，不全量通读）。
4. 执行后补全记录到 `logs/`（仅对有价值任务）。

## 设计原则

- 短总则：必须短、可执行、可检查。
- 分层读取：总则必读，专题按需读。
- 模板优先：减少自由发挥导致的风格漂移。
- 可复盘：重要任务留痕，便于迭代规则。

## 命名规范

`ai-agent/` 里的 Markdown 文件名用小写 `kebab-case`，`logs/` 里建议 `YYYY-MM-DD-简短主题.md`，新增文件时优先和同目录已有文件保持同一种风格。

## 常见维护动作

- 新增规则：先改 `rules/`，再视需要同步 `.cursor/skills/` 下的 `SKILL.md` 描述。
- 新增流程：优先改 `templates/`，确保输出结构保持一致。
- 经验沉淀：重要任务结束后补 `logs/`，避免口头经验丢失。

## 协作变更检查清单

调整协作方式（规则、模板、必读列表、收尾输出结构）时，建议按顺序自检：

- [ ] `rules/`、`templates/`、`goals/` 中相关内容已更新。
- [ ] 新增 `rules/*-rules.md` 等专题文件时，已在 [`INDEX.md`](./INDEX.md)「按需读取」中增加对应一条，避免 INDEX 与事实脱节。
- [ ] `.cursor/skills/ai-agent-frontend-task/SKILL.md`、`ai-agent-generic-task/SKILL.md` 与 [`SKILL.md`](./SKILL.md) 中的执行流程、收尾输出说明保持一致（Cursor 以 `.cursor/skills/` 为实际触发入口）。
- [ ] 若修改收尾输出字段，已同步 `rules/must-follow.md` 第 6 条与上述三份 Skill。
